# Финансовое ядро

Первый проверяемый сценарий: арифметика обычной покупки в RUB, финальные цены с включённым налогом, отдельная ещё не применённая скидка, округление каждой строки HALF_UP до копеек. Это ограниченный контракт, а не универсальный стандарт для любых чеков. complete и confirmed должны быть true только после проверки полноты и подтверждения всех полей и семантики скидки/округления. Неподдерживаемые документы, возвраты, разные валюты, авансы, неизвестные правила округления, уже применённые скидки и налоги вне цены должны передаваться на уточнение, а не преобразовываться в этот контракт без проверки. Не суммировать расхождение строки и итога как независимые потери.

Запуск без Android SDK: `kotlinc core/src/main/kotlin/fincontrol/core/ReceiptAudit.kt core/src/test/kotlin/fincontrol/core/ReceiptAuditTest.kt -include-runtime -d /tmp/fin-control-tests.jar && java -jar /tmp/fin-control-tests.jar`. Kotlin 1.9.0 / JDK 21. Тесты синтетические, 18 сценариев; не являются оценкой OCR или Android.

## Подтверждение OCR-суммы (JVM-контракт)

`ReceiptTotalReview` принимает только наблюдаемые в исходной OCR-строке суммы, привязку к координатам строки и confidence >= 8500/10000. Не выбирает сумму автоматически; требует явного выбора пользователем и актуальной версии снимка. Возвращаемый `UserVerifiedTotal` **не** означает подтверждения всего чека: расчёты и выводы выполняются только после отдельно подтверждённой полноты документа, валюты, налогов, скидок, количества и округления. Не подключено к Android/OCR runtime.

Все 69 синтетических JVM-сценариев (18 чеков, 24 сравнения/аванса и 27 проверки OCR-источников) запускаются через workflow `.github/workflows/receipt-review-core.yml` на Kotlin 1.9.0/JDK 21. Это не испытание Android-приложения или реальных финансовых данных.
